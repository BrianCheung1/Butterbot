# Phase 0 SQLite capacity experiment

## Status and scope

**Slice 0.3 accepted on 2026-08-25 for the documented launch assumption.** SQLite passed three
open-loop runs at the required twice-projected-peak rate on the current development host. This
accepts the candidate persistence and operating-mode gate; it does not make Phase 0 complete,
authorize the first migration, or approve public gameplay.

The experiment uses fresh temporary databases and a disposable `bench_*` schema. It exercises
player/wallet creation, credits, sufficient-funds and optimistic-version-guarded debits,
transport replay, fingerprint mismatch, domain uniqueness, balanced ledger postings, rollback,
WAL reads/checkpoints, busy timeout, and bounded retries. It creates no Alembic revision and is
not a production schema proposal.

The final mining transaction remains a separate pre-public gate because this candidate workload
does not contain inventory, XP, opportunity state, item movements, action facts, durable
restriction checks, or production telemetry.

## Accepted projected peak

The accepted planning peak is **17 mutation transactions/second**; the SQLite acceptance target
is **34 offered transactions/second**. `decisions.md` records the complete derivation. In summary:

| Input | Accepted assumption |
| --- | ---: |
| Launch active population | 1,000 players |
| Peak overlapping sessions | 100 (10%) |
| Peak command cadence | One command/session/10 seconds |
| Mutation share of modeled commands | 95.30% |
| Normal interactive writes | 9.53 TPS |
| Join burst | 100 joins/60 seconds = 1.67 TPS |
| Arrival/model-error factor | 1.5 |
| Result | `(9.53 + 1.67) × 1.5 = 16.80`, rounded up to 17 TPS |
| Required offered rate | `2 × 17 = 34 TPS` |

The 95.30% share comes from the Phase 0 cohort mix: 9.71 daily profession actions, 2.43
conversion/spending mutations, 0.74 daily claims, and 0.11 weekly-objective claims divided by
13.63 modeled commands. These are reviewable launch-planning assumptions, not observed traffic;
a material change requires a replacement decision and rerun.

## Reproduction

From the repository root with the development environment installed:

```powershell
.venv\Scripts\python.exe -m benchmarks.sqlite_capacity `
  --saturation-concurrency 1,4,8,16 `
  --saturation-operations 800 `
  --seed-accounts 64 `
  --projected-peak-tps 17 `
  --offered-tps 34 `
  --warmup-seconds 10 `
  --measurement-seconds 30 `
  --repeats 3 `
  --workers 4 `
  --storage-description "Local C: temporary-directory storage on the development host; deployment host and physical media are not yet selected." `
  --output docs/evidence/sqlite-capacity-2026-08-25.json
```

The gate is open-loop: arrivals are scheduled independently of completion at 34 TPS. Queue delay
is included in end-to-end latency and also reported separately; incomplete work and drain time
are visible as measurement-window backlog rather than hidden by closed-loop throttling. Each
repeat uses a fresh database and four persistent writer connections.

The workload is 20% unique join, 40% credit, and 40% guarded debit. Debits target a four-wallet
hot set, require sufficient balance, and update the expected balance version. Each monetary
mutation claims transport identity and a separate business entitlement, writes a transaction,
two non-zero balanced postings, and two balance projections in one transaction.

Ten seconds warms connections and drives 340 mutations through the WAL before measurement.
Thirty seconds schedules 1,020 measured operations, long enough to exercise steady scheduling
and checkpoint pressure rather than a roughly one-second burst. Three fresh-database repeats
provide 90 measured seconds and 3,060 measured operations while keeping the Phase 0 workflow
practical. This is architecture evidence, not a statistical production load certification.

The JSON records its generation time, exact configuration, environment/storage description,
observed pragmas, every open-loop repeat, saturation diagnostics, correctness diagnostics, and
capacity assessment. It also stores a SHA-256 fingerprint of `benchmarks/sqlite_capacity.py`.
Ordinary pytest fails if the checked evidence was generated by a different benchmark
implementation or does not use the accepted gate configuration.

## Environment

The accepted run used Windows 11 build 26200, an AMD64 Family 23 Model 113 processor, 12 logical
CPUs, Python 3.13.15, SQLite 3.50.4, and aiosqlite 0.22.1. Temporary databases were on the local
`C:` volume. The evidence records volume size/free space and explicitly notes that deployment
host and physical media are not selected. The result is therefore valid for the Phase 0
architecture decision and must be repeated on the selected deployment host before public
economic mutations.

Raw evidence: [`evidence/sqlite-capacity-2026-08-25.json`](evidence/sqlite-capacity-2026-08-25.json).
The JSON is canonical; the summary tables below are transcriptions of its checked values. This
documentation-only synchronization does not regenerate evidence or reset its freshness contract.

## Twice-peak results

All runs offered and completed 34.0 TPS inside the measurement window. There was no backlog or
drain beyond scheduler granularity, no retry, no final lock failure, and no invariant failure.

| Repeat | Offered TPS | Completed-in-window TPS | p95 | p99 | Max | Service p99 | Queue-delay p99 | Lock-held p99 | Result |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 34.0 | 34.0 | 17.432 ms | 18.356 ms | 21.275 ms | 6.816 ms | 15.636 ms | 6.260 ms | pass |
| 2 | 34.0 | 34.0 | 17.601 ms | 18.595 ms | 21.711 ms | 6.249 ms | 15.700 ms | 5.790 ms | pass |
| 3 | 34.0 | 34.0 | 17.492 ms | 18.238 ms | 24.183 ms | 6.388 ms | 15.551 ms | 6.006 ms | pass |

The acceptance criteria remain p95 at most 100 ms, p99 at most 250 ms, fewer than 1% of
operations requiring a busy retry, no final lock failure, no invariant/idempotency failure, and
at least 99% completion inside each measurement window. Every repeat passed.

## Correctness diagnostics

- Sixteen distinct transport requests for one Discord identity produced one player, one wallet,
  one `created` result, and fifteen existing/domain-replay results.
- An injected failure after request, ledger, and projection writes but before postings rolled
  back every write and restored the starting wallet.
- A reader completed in 0.292 ms during an uncommitted writer and observed the prior committed
  value, confirming WAL reader/writer behavior.
- The configured 1,000 ms busy timeout raised `database is locked` after 1,163.248 ms.
- A transient lock recovered on attempt two in 1,459.621 ms; a persistent lock stopped after
  three attempts in 2,914.607 ms, both within the three-second policy budget.
- Sixteen guarded debits competing for a five-coin wallet applied exactly five, rejected eleven,
  ended at zero, wrote five ledger transactions, and retired five coins.
- Same-key/same-fingerprint replay returned the prior result; same-key/different-fingerprint was
  rejected; a distinct transport key for the same business entitlement did not apply again.

## Saturation diagnostic and safe envelope

Closed-loop saturation is retained only to expose the contention boundary and calculate
provisional operational warning thresholds. It is not the twice-peak acceptance test.

| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 588.784 | 2.051 ms | 3.755 ms | 0.000% | 0 | pass |
| 4 | 499.505 | 2.524 ms | 171.927 ms | 0.000% | 0 | pass |
| 8 | 390.104 | 2.605 ms | 656.098 ms | 0.500% | 0 | fail: p99 |
| 16 | 326.932 | 3.888 ms | 1,639.439 ms | 1.500% | 0 | fail: p99 and retry rate |

For this candidate workload on this host, keep one process and at most four in-flight writer
transactions. The provisional PostgreSQL-start planning rate is 249.75 TPS (50% of the passing
four-writer diagnostic), and the provisional migration-completion rate is 349.65 TPS (70%). The
accepted 17 TPS projected peak is 6.8% of the start threshold, and the repeated 34 TPS gate passed.

The Phase 0 SQLite capacity gate therefore passes, and the load result does **not** trigger
PostgreSQL. Independent triggers remain unchanged: a second process, unmet backup/availability
objectives, reporting pressure, three peak windows over the latency/retry limits, or final lock
failures still start migration work.

## Operating requirements

- one bot/worker process;
- `foreign_keys=ON` on every connection;
- persistent WAL and `synchronous=FULL`;
- `busy_timeout=1000` ms on every connection;
- at most two busy retries with 25/75 ms backoff inside a three-second budget;
- preserve the original transport key, fingerprint, and business key across retries;
- retry only busy/locked failures, never domain rejection or constraint failure;
- no Discord, network, sleep, or user wait inside a transaction; and
- target at most 50 ms from writer-lock acquisition through commit while retaining the stricter
  end-to-end p95/p99 gates.

## Remaining prerequisites

Slice 0.3 remains accepted. Slice 0.4 has now selected the operations contract in
`operations.md`, but only the explicit Final Phase 0 Gate Review can declare Phase 0 complete and
authorize the first production economy migration. No baseline migration is part of Slice 0.4.

The deployment-host rerun is a pre-public-durable-mutation requirement because that host is not
yet selected. It uses the exact accepted open-loop configuration and diagnostics on the real
database volume under normal host agents. Every repeat must still satisfy 99% in-window
completion, p95 at most 100 ms, p99 at most 250 ms, retry rate below 1%, no final lock, backlog,
invariant or idempotency failure, and all correctness diagnostics. Failure keeps mutations
disabled and requires host/storage remediation, replacement evidence, or PostgreSQL—not a weaker
gate.
